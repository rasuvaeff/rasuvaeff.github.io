Almost every web application stores files people upload: avatars, invoices, photos for a news item, an image pasted into a rich-text editor. And almost every one does it in a hurry: `move_uploaded_file()` into `public/uploads`, the extension taken from the client, the path saved in some text column. That works until somebody uploads an HTML file, a 60000×60000 JPEG, or until a cleanup script deletes a picture that one forgotten page still links to.

[yii3-filestorage](/packages/yii3-filestorage) is my answer for Yii3. It is a family of six packages, and on 28 November 2026 all six were released together after a two-pass review before 1.0. This post describes everything the family can do and why you would need each part. Figures are as of 2026-11-28.

---

## What a file goes through

Between "the browser sent a file" and "nobody needs it any more" a file passes several stages, and each one has its own way of going wrong:

| Stage | What can go wrong |
|---|---|
| Accepting | the client lies about the type; a small file decodes into gigabytes of pixels; a filename carries control characters |
| Storing | a path built from user input; a half-written file visible to readers; local disk today, S3 tomorrow |
| Describing | where the metadata lives; which tenant a file belongs to |
| Serving | an HTML or SVG file served inline from your own origin is stored XSS; a private file needs an expiring link; video needs `Range` |
| Deriving | thumbnails with arbitrary sizes from the URL; the same rendition generated by 50 requests at once |
| Sharing | two people upload the same bytes, and deleting one must not delete the other |
| Deleting | a file is still referenced from text somewhere; a mistaken sweep cannot be undone |

The family covers all of these stages. You install only the parts you need.

## The packages

| Package | Version | What it gives | You need it when |
|---|---|---|---|
| [`yii3-filestorage`](/packages/yii3-filestorage) | 0.10.0 | Facade, upload policies, local stores, layouts, signed-token format, all console commands except two | always |

| [`yii3-filestorage-web`](/packages/yii3-filestorage-web) | 0.7.0 | Signed download URLs, a download action with `Range`/`ETag`/`304`, an upload action | private files are downloaded through the application |
| [`yii3-filestorage-images`](/packages/yii3-filestorage-images) | 0.9.0 | Named-preset thumbnails, GD/Imagick, PDF previews, SVG sanitizer, `filestorage:warm` | you need image renditions |
| [`yii3-filestorage-attachments`](/packages/yii3-filestorage-attachments) | 0.6.0 | Links between files and owners: an order's invoice, a user's avatar | files belong to entities and you have no Active Record |

PHP 8.3–8.6 for the core, `-flysystem` and `-images`; 8.3–8.5 for `-db`, `-web` and `-attachments`. All six are 0.x. The README of the core explains what that means: the path layout and the token format are already frozen, and 1.0 is waiting for time in production on the backends.

## Architecture: a facade and two swappable halves

The core is one facade, `StorageInterface`, with `add()`, `find()`, `remove()`, `stream()` and `urlFor()`. Behind it there are two contracts:

- `StoreInterface` is where the bytes live: a local directory, a bucket.
- `RepositoryInterface` is where the metadata lives: in practice a database table.

**The core binds neither of them.** Which disk and which database you use is a decision of your deployment, and `yiisoft/config` allows exactly one vendor package to define a DI key. If the core bound a default store and `-flysystem` bound its own, the configuration would fail with `Duplicate key`. So the core binds the facade and its own services, `-db` binds the repository and the ledger, `-flysystem` binds the store, `-web` binds the signer and the URL generator, `-images` binds the presets and the processor. Every package owns only its own keys, so any combination of the six merges without conflicts. I check this with a harness that installs the whole family into a throwaway application and merges the configuration the same way the Yii3 runner does.

The facade is a plain interface with a `final` implementation, so quotas, metrics or antivirus scanning are decorators you write, not packages you install. The core binds it under two ids: `Storage::class` builds the facade, and `StorageInterface::class` is an alias for it. A decorator bound to the interface takes `Storage::class`. If it asked for the interface, the container would hand it to itself and answer `CircularReferenceException`.

```php
// config/common/di/filestorage.php
use Rasuvaeff\Yii3Filestorage\Storage;
use Rasuvaeff\Yii3Filestorage\StorageInterface;

return [
    StorageInterface::class => static fn (Storage $inner, Quotas $quotas): StorageInterface
        => new QuotaStorage($inner, $quotas),
];
```

## Getting started: local disk

The smallest working setup is one binding for the store. The repository comes from `-db`; for a first try the core ships `Test\MemoryRepository`, which forgets everything when the process ends.

```php
// config/common/di/filestorage.php
use Psr\Http\Message\StreamFactoryInterface;
use Rasuvaeff\Yii3Filestorage\Store\FileSystem\FileSystemStore;
use Rasuvaeff\Yii3Filestorage\Store\StoreInterface;

return [
    StoreInterface::class => static fn (StreamFactoryInterface $streams): StoreInterface
        => new FileSystemStore(
            name: 'upload',
            rootPath: '/app/runtime/upload',
            streamFactory: $streams,
            quarantinePath: '/app/runtime/upload-quarantine', // where gc moves what it deletes
        ),
];
```

Then `./yii filestorage:check` prints the wiring, the layout and capabilities of each store, the tenancy mode and the rules of each group, and fails on combinations that are unsafe. More about them below.

## Storing and reading

A file can come from four places, and each one turns into an `Upload`:

```php
$file = $storage->add(
    Upload::fromUploadedFile($request->getUploadedFiles()['avatar'], $streamFactory),
    groupName: 'avatars',
);

$file = $storage->add(
    Upload::fromStream($pdfStream, 'invoice-2026-08.pdf', $streamFactory), // a generated PDF
    groupName: 'documents',
    metadata: ['invoiceId' => 4711],
);

$file = $storage->add(Upload::fromPath('/tmp/import.csv', $streamFactory));

$file = $storage->add(Upload::fromDataUrl( // rich-text editors, JSON APIs
    'data:image/png;base64,' . $base64Payload,
    'logo.png',
    $streamFactory,
    $clientHint,
    maxSpoolBytes: 5_242_880,
));
```

`Upload` normalises the client's filename once: it removes control and bidi characters (U+202E turns `invoice<U+202E>gpj.exe` into a visible `invoiceexe.jpg`), replaces invalid UTF-8 and cuts the name to 255 characters keeping the extension. The name stays metadata and never enters a path. A non-seekable body is spooled with a cap, so sniffing, policy, hashing and writing can all read one input.

The result is an immutable `File`: id (UUIDv7 by default), store, group, path, original name, detected type, size, description, hash, metadata and timestamps. Reading is `stream()` (PSR-7, the default), `content()` (capped by `maxInlineBytes`, 8 MiB by default) and `exists()`. Metadata is updated through `File::withMetadata()` and `save()`, and the new timestamp matters: `updatedAt` is part of the download validator.

Every `add()` is all-or-nothing: either a row with its object, or nothing. Everything the caller passes is validated before the write. Anything that fails after the write is an `AddException`, and the written object is deleted. There is deliberately no `addMany()`: a batch cannot be atomic over a filesystem or an object store, and a method with that name would promise that it is.

## Accepting files safely

### Groups and policies

A group is a use case, not a folder. Its rules are set once in `params`, instead of validating before every `add()`:

```php
// config/common/params.php
return [
    'rasuvaeff/yii3-filestorage' => [
        'policies' => [
            'avatars' => [
                'allowedMimeTypes' => ['image/jpeg', 'image/png', 'image/webp'],
                'maxBytes' => 5_242_880,
                'maxPixels' => 40_000_000,
                'requireImageDimensions' => true,
            ],
            'documents' => ['allowedMimeTypes' => ['application/pdf'], 'maxBytes' => 52_428_800],
            '*' => ['maxBytes' => 20_971_520],
        ],
        'delivery' => [
            '*' => ['allowDirectPublicUrl' => false, 'forceDownload' => true],
        ],
    ],
];
```

A rejected upload throws before the store is touched, and the exceptions map onto HTTP statuses:

```php
try {
    $file = $storage->add($upload, groupName: 'avatars');
} catch (SizeLimitExceededException) {
    // 413: maxBytes, the spool cap, a data URL over its cap, upload_max_filesize
} catch (UnsupportedMediaTypeException $e) {
    // 415
} catch (PolicyViolationException $e) {
    // 400/422: pixel limit, unmeasurable image
}
```

On local stores `maxBytes` is enforced **while the bytes are copied**, not after: a body of unknown length is stopped when it crosses the limit, and the partial object is removed.

### The type comes from the content

Only `finfo` output counts. The type the client sent is kept for diagnostics and never reaches a policy, a path or a `Content-Type` header. The file extension comes from the detected type through the `symfony/mime` table. Scriptable types (HTML, SVG, XML and every `+xml`, JavaScript) and types known by an executable extension are stored as `.bin`, unless you opt back in with `extensionOverrides`.

### Decompression bombs

`maxPixels` (40 million by default) is read from the image header, and pixels are never decoded. The review found that a fixed header window is not enough, so each format is walked in its own way:

- **JPEG** is walked marker by marker to the frame header. Before 0.10 a 325 KB file with 60000×60000 pixels passed every policy: APPn padding pushed the frame header past the first 256 KiB, and "dimensions not found" meant "skip the check". A second frame header before the scan is refused too.
- **GIF** is walked block by block. `getimagesize()` reports the logical screen, but a decoder allocates every frame at its own size, so a 47 KB file with a 1×1 screen around an 8000×8000 frame passed the check. A frame that does not fit inside its screen is now refused.
- **TIFF** is measured from its directory chain wherever the writer put it.

A JPEG, PNG, GIF, WebP or TIFF whose dimensions cannot be established is **refused**. Other raster formats (AVIF, HEIC…) are measured from the first 256 KiB, and `requireImageDimensions` refuses them when the size is not found there.

### Active content

The family has one list of active types, `Mime\ActiveMediaTypes`, in one configured instance. There are two tiers: scriptable types (HTML, XHTML, SVG, XML and any `+xml` type, XSLT, MathML, JavaScript, RSS/Atom) and plugin types (PDF, Flash). Whatever a group's policy says, every type on the list is delivered as an attachment: by the proxy, by a presigned S3 URL, everywhere. `filestorage:check` fails if a group with direct public URLs accepts scriptable types. `activeMediaTypes.extra` adds types, and `allowInline` lets plugin types out, so a PDF can be shown inline. A scriptable type cannot be let out.

Before 0.10 there were two lists, with 10 types in `-web` and 5 in `check`, and a presigned S3 URL served SVG inline. Now there is a single list.

Two things the core does not do for you, and says so: EXIF with GPS coordinates stays in the original (`-images` has a re-encoding decorator in its examples), and an SVG served from your origin is a program. For SVG there is an opt-in sanitizer in `-images`.

## URLs: public, presigned, proxied

There is one method to call: `$storage->urlFor($file)`. It applies the group's delivery policy and then tries in order:

1. a permanent public URL, but **only** if the group explicitly allows one;
2. a presigned URL from the store (S3 through `-flysystem`);
3. the application's signed proxy URL (`-web`).

A presigned URL bypasses the application, so the headers S3 attaches become the response. If the URL cannot carry the disposition and type the policy demands, the store returns no URL, and the call falls back to the proxy, which sets the headers itself. Templates do not need to branch on whether a store happens to be public.

### The proxy in -web

[`yii3-filestorage-web`](/packages/yii3-filestorage-web) mints tokens of a frozen format, `v1.<key-id>.<expires>.<payload>.<hmac>`, HMAC-SHA256 over everything before the signature. The payload holds the file id, the variant and the tenant. Installing it is enough: `urlFor()` starts returning signed URLs for private stores.

```php
// config/common/routes.php
use Rasuvaeff\Yii3FilestorageWeb\Action\FileDownloadAction;
use Yiisoft\Router\Route;

return [
    Route::get('/files/{token}')->action(FileDownloadAction::class)->name('file/download'),
];
```

What the download action guarantees:

| Rule | Why |
|---|---|
| Every failure is a 404: bad signature, expired token, wrong tenant, missing bytes | a 403 would confirm that the id exists |
| The tenant comes from the token, never from the request | a signed link works without a session, and a leaked id resolves to nothing in another tenant |
| Conditional requests are answered before the store is opened | a `304` costs one metadata read; a thumbnail is not generated to answer one |
| `If-Modified-Since` confirms only an inline response | the `ETag` carries the disposition, a date does not; otherwise a cached `inline` copy survives a switch to `forceDownload` |
| Active content is an attachment, with `nosniff` | stored XSS from your own origin |
| A token minted for a thumbnail is not served the original | the variant is inside the signature |

Ranges are served when they can be cheap, which is a question about the store: a store with a range primitive gets one ranged read, a seekable local file is windowed with a seek, and a forward-only S3 body gets an honest full `200` without `Accept-Ranges`. A single range gives `206`, a request past the end gives `416`, and `If-Range` restarts a download of a file that changed instead of splicing two files together.

Signing keys rotate without breaking links that are already in inboxes, because the key id is part of the signed envelope. A link minted outside a request (a queued email, a report) has no current tenant; `forScope()` of `HmacProxyUrlGenerator` stamps it explicitly (`withProxyUrls()` is a method of the concrete `Storage` and of `-db`'s `DeduplicatingStorage`, not of `StorageInterface`):

```php
$url = $storage->withProxyUrls($proxyUrls->forScope($tenantId))->urlFor($file);
```

The other half of `-web` is `FileUploadAction`: one file per request (a multi-upload cannot be atomic either), `201` with JSON, `413`, `415`, `400`, `500` for errors no client can fix. `Validation\FileRule` repeats the checks at form level for `yiisoft/validator`, so the error appears next to the field, while the authoritative checks still run in `add()`.

## How files lie on disk

### Two layouts

`DirectoryLayout` is the frozen default: every file gets its own directory, `<…>/<key>/original.<ext>`, and `delete()` removes the directory. That is why a thumbnail can live at `<key>/thumb-v1.webp` without a schema change, and why deleting a file never leaves its renditions behind.

`FlatSiblingLayout` is chosen once per store, before it holds data. It is for flat content-addressed trees such as `blobs/ab/cd/<sha>.<ext>`, with renditions next to the original as `<sha>-thumb-v1.webp`. `FlatSha256KeyGenerator(prefix: 'blobs')` adopts an existing tree of that shape as it is. Its keys ignore the tenant, so it is for a single-tenant installation.

### The pair must match

The worst first-pass finding was here. A key generator and a layout are configured in two different places, and a flat key under `DirectoryLayout` made deleting one blob delete its whole `ab/cd/` directory together with every neighbour that shares the first four hex digits. Three of the four reports found it independently. Now `DirectoryLayout` refuses a file that is not named `original[.<ext>]`, and `LayoutCompatibility` checks the pair behaviourally: it takes two keys from one directory and asks the layout what deleting each would remove. The `-db` factory, the `-flysystem` DI and `filestorage:check` all call it.

### A web root shared with the application

A public directory usually also holds the application's own files. `gc --orphans` treats everything under a store root with no row as an orphan, so the root belongs to the store. Hidden entries (`.htaccess`, `.well-known/`) are never listed, and `ownedPrefixes` limits the inventory to the store's own subtrees and refuses writes outside them. `webRoot` lets `PublicFileSystemStore` refuse a quarantine inside the document root.

```php
$store = new PublicFileSystemStore(
    new FileSystemStore(
        name: 'uploads',
        rootPath: '/app/public/uploads',
        streamFactory: $streams,
        quarantinePath: '/app/runtime/uploads-quarantine',
        layout: new FlatSiblingLayout(),
        ownedPrefixes: ['blobs', 'files'],
    ),
    baseUrl: '/uploads',
    webRoot: '/app/public',
);
```

Since 0.10 both local stores are content-addressable: they write under a random `.part` name and publish with `link()`, which refuses an existing target. Two writers of the same bytes both succeed, and deduplication now works on a local disk too, public or not. One honest warning from the README: on a public store a content key is the SHA-256 of the bytes, so anyone holding the same bytes can compute the URL. Keep private groups out of a content-addressed public store.

## Metadata in a database: -db

[`yii3-filestorage-db`](/packages/yii3-filestorage-db) stores rows in three tables, `filestorage_file`, `filestorage_blob` and `filestorage_blob_reservation`. Migrations are registered by namespace and need `yiisoft/db-migration` ^2.1: on 2.0 that registration silently found nothing and `migrate:up` exited 0 without creating a table. The integration suite runs this recipe on every build.

### Tenants

Bind `FileScopeProviderInterface`, and every statement the package issues gets a `scope_id` predicate. There is no method that skips it for a resolved tenant. A signed download has no ambient tenant, and the shortcut everybody reaches for is to turn the filter off for downloads. That is a cross-tenant read of every file whose id leaks. Instead the tenant travels inside the HMAC, and `ScopedFileResolverInterface` matches it as a second predicate.

Three things changed in 0.4:

- **A provider that returns `null` is refused.** Before, a tenant that did not resolve (an anonymous route, a job without its context) dropped the predicate, and `find()` saw every tenant's rows. Now it is `MissingScopeException`.
- **Global access is an explicit opt-in for maintenance**, `globalMaintenanceAccess`. It reaches only the two keys the maintenance commands resolve, so a queue worker that shares the console params still gets the refusal.
- **Tenants are compared byte for byte on MySQL and MariaDB too.** Their default collations treat `Acme`, `acme` and `Acmé` as one tenant. The migration switches to a binary NO PAD collation (`utf8mb4_0900_bin` or `utf8mb4_nopad_bin`). The first fix used `utf8mb4_bin`, which is PAD SPACE: the second review pass found that `acme ` and `acme` became one tenant, a match MySQL 8 by default never made.

## Deduplication

Two people upload the same file. One object on disk, two rows, and the object must not disappear when the first row does. Ownership is a physical `BlobId` (one object in one store), never a hash: a hash is the same across stores, groups and tenants, and a hash-keyed counter lets one tenant delete what another is reading. There is no `reference_count` column either: a reference *is* a file row pointing at the blob, and the guards ask `NOT EXISTS`.

The protocol is reserve, publish, commit:

```php
$blob = BlobId::create('upload', $contentAddressedPath);

$reservation = $ledger->reserve($blob, $sha256, $size, $expiresAt); // claim the key
$store->putIfAbsent($upload, $blob->object);                         // publish the bytes
$ledger->commit($reservation, $file);                                // row + reference, one transaction
```

The rule the design turns on: **shared bytes are never deleted inside a request.** The last release only marks a blob `pending_delete`. Only the collector deletes, only under an exclusive expiring lease, and only while the reference and reservation counts are still zero in the same statement that claims the blob. A `SELECT` followed by an `UPDATE` is two moments with a gap, and the gap is where a committed row ends up pointing at deleted bytes.

You do not drive the protocol by hand. Deduplication is turned on by rebinding the facade:

```php
// config/common/di/filestorage.php
use Rasuvaeff\Yii3Filestorage\StorageInterface;
use Rasuvaeff\Yii3FilestorageDb\DedupScope;
use Rasuvaeff\Yii3FilestorageDb\DeduplicatingStorageFactory;

return [
    StorageInterface::class => static fn (DeduplicatingStorageFactory $factory): StorageInterface
        => $factory->create(
            scope: DedupScope::TenantGroup,
            dedupMaxBytes: 104_857_600,
            deleteGracePeriod: new DateInterval('PT1H'),
        ),
];
```

`DedupScope` is a security choice, not a dial for space: `TenantGroup` (the default, safe for untrusted tenants), `Tenant`, or `Global`, which saves the most and reveals across tenants whether a given file already existed (the write timing and a quota that does not move both show it). The factory refuses five configurations that would lose data quietly: a store that is not content-addressable, a ledger other than `DbBlobLedger`, a ledger on a different connection than the repository (then `commit()` is two transactions), content keys the layout cannot delete one by one, and, under tenancy, a key generator that leaves the tenant out of the key.

Files above `dedupMaxBytes` silently take the unique path: the key is the hash, and choosing it means reading the whole body first.

On MySQL the ledger runs its transactions at `READ COMMITTED`. Under REPEATABLE READ, MariaDB 11.6.2+ with `innodb_snapshot_isolation` (on by default) fails a read-then-update with error 1020 whenever another connection changed the row, for example when two people upload one file at the same moment. MySQL never does this, so only the MariaDB leg of CI saw it.

Existing data is migrated with `filestorage:deduplicate`. It reads every row, hashes it, publishes with `putIfAbsent()` and repoints the row through the same `commit()`. A crash leaves either the old row or the new one. The old object is left behind on purpose: readers may still hold its path, and `gc --orphans` reclaims it later.

## Deleting: two-phase garbage collection

`filestorage:gc` is the only thing in the family that deletes bytes another request might want. Since 0.9 it never deletes at once:

1. the bytes are moved into the store's **quarantine**, outside the root and outside anything the web server serves;
2. the decision is committed in the ledger;
3. only then are the bytes purged, or restored with put-if-absent semantics if the commit was refused.

A collector paused past its lease used to delete bytes that a writer had re-published in the meantime. Now its commit is refused, and the bytes go back.

| Rule | What it protects |
|---|---|
| An orphan is a candidate only after `--min-age` (1 hour), measured after its page was listed; an object with no timestamp never is | uploads between publishing the bytes and saving the row; `--orphans --apply` no longer needs uploads stopped |
| Orphans and released files stay in the quarantine for `--retention` (7 days) | a mistaken sweep can be undone for a week |
| Every quarantine entry is checked against the rows and the reference checker on every run | a file referenced again comes back at once |
| One bad entry is skipped and counted, not the end of the run | one broken entry used to stop the whole quarantine on every run |
| `.part` files of crashed writes are removed by age | before, nothing ever collected them, and a public root served them |
| `gc --orphans` refuses under a bound tenant provider | rows filtered by tenant cannot prove an object unreferenced; the sweep would delete every other tenant's files |

`gc`, `backfill-hash` and `deduplicate` report by default and act only with `--apply`. A command whose first run deletes is one somebody eventually runs against the wrong database.

### When references are URLs inside text

By default a row *is* the reference: the file lives until the application removes the row. But many applications reference files as URLs inside HTML, Markdown or JSON. For such groups you set `'referencesOwnedBy' => 'application'` and bind a `ReferenceCheckerInterface`, which answers per page, in a batch, which paths are still mentioned:

```php
final readonly class TextColumnReferences implements ReferenceCheckerInterface
{
    public function referenced(string $storeName, array $objects): array
    {
        return array_values(array_filter(
            $objects,
            fn (StoredObjectId $object): bool => $this->index->mentions($object->relativePath),
        ));
    }
}
```

`gc` then releases rows the checker no longer names, older than `--min-age`, and asks again right before quarantining a blob, so a URL pasted back in the meantime keeps its bytes.

The family was tried on a real application, a production fan site, before the release, and that trial added two traps to the README. Both are easy to fall into:

- **Skip the package's own tables.** `filestorage_file.relative_path` names every stored file. A scan over "every text column" that includes it answers "referenced" for every row, and nothing is ever released.
- **Match every form the application writes.** A URL (`/uploads/blobs/…`) and a path inside the store (`blobs/…`, kept by an image cache column, say) are both references. A checker that looks for one form releases files the other form still names.

## Object stores: -flysystem

[`yii3-filestorage-flysystem`](/packages/yii3-filestorage-flysystem) is one `FlysystemStore` class for every adapter. Adapters really differ, and a PHP interface cannot be implemented conditionally at runtime, so the store reports its capabilities as results rather than as interfaces. URLs are always implemented and return `null` when the adapter cannot mint one. There is no `Range`: `readStream()` returns the whole object and an S3 body is not seekable, and pretending otherwise would turn "seek to the last minute" into a full download. For S3 a presigned URL handles ranges natively.

Presigned URLs are issued only through an explicit mapping, `S3TemporaryUrlOptions`, which signs `ResponseContentType` and `ResponseContentDisposition` into the URL. Without the mapping there is no presigned URL, and the proxy serves the file. Active types are signed as `attachment`, because an S3 response cannot carry `nosniff`. A stored type that does not follow RFC 9110 grammar is signed as `application/octet-stream`: simply stripping CR/LF glued `image/svg+xml\r\nX: y` into `image/svg+xmlX: y`, a type on no list.

What else is in it:

- **One listing per `gc` pass.** In 0.4 every page re-listed the bucket from the start: for 10,000 objects without `orderedListing`, 425,397 entries pulled. Now a page continues the previous page's listing.
- **`orderedListing` is verified, not trusted.** A wrongly declared order silently lost objects: the probe saw 1,067 of 10,000. Now every consecutive pair is compared, and the first key out of order stops the pass with an error.
- **The quarantine** lives under a prefix starting with `.` or `_`, and moves into it carry `ACL: private`. Otherwise Flysystem's S3 copy keeps the public ACL, and a deleted public object stays downloadable for the whole retention.
- **`publicBucket`** is your statement that the bucket serves objects without credentials. `check` then fails every group that accepts active content. The store does not guess it: an S3 adapter builds an object URL for a private bucket too.
- **Byte caps.** A remote `PUT` cannot be aborted halfway, so the cap is checked before the write and verified after it, and an object that under-reported its size is removed.
- **Deduplication** only through `FlysystemContentAddressableStore` with an explicit `AdapterSemantics`: atomic visibility and immutable content keys. There is no permissive default. Without them, `fileExists()` then `write()` hands a second writer a half-uploaded object and calls it a cache hit.

```php
return [
    StoreInterface::class => static fn (
        FilesystemOperator $filesystem,
        StreamFactoryInterface $streams,
        ActiveMediaTypes $activeTypes,
    ): StoreInterface => new FlysystemContentAddressableStore(
        store: new FlysystemStore(
            name: 's3',
            filesystem: $filesystem,
            streamFactory: $streams,
            temporaryUrlOptions: new S3TemporaryUrlOptions($activeTypes),
            quarantinePrefix: '.quarantine',
            orderedListing: true,
        ),
        semantics: AdapterSemantics::guaranteed(),
    ),
];
```

The integration suite runs against SeaweedFS, a real S3 gateway: MinIO's images disappeared from Docker Hub in September.

## Images: -images

[`yii3-filestorage-images`](/packages/yii3-filestorage-images) produces renditions from **named presets only**. `w=200&h=200` in a URL, even a signed one, turns one upload into an unbounded set of addressable derivatives; a whitelist makes the set finite.

```php
// config/common/params.php
return [
    'rasuvaeff/yii3-filestorage-images' => [
        'presets' => [
            'thumb' => ['version' => 1, 'width' => 200, 'height' => 200, 'fit' => 'cover', 'format' => 'webp', 'quality' => 82],
            'poster' => ['width' => 1280, 'format' => 'jpeg'],
        ],
    ],
];
```

```php
$url = $derivatives->urlFor($file, 'thumb');
$srcset = Srcset::for($derivatives, $presets, $file, ['thumb', 'poster']); // "url 200w, url 1280w"
```

- **The version is part of the name** (`thumb-v2.webp`). Changing a preset's settings under the same name would keep serving old renditions; bumping `version` creates a new object.
- **Lazy, with a stampede lock.** The first request generates the rendition, every later one reads it. The lock is keyed by the physical rendition, so under deduplication requests for different rows sharing one object still generate once. `filestorage:warm` pre-generates through the same locked path.
- **Dimensions at upload.** `ImageMetadataStorage` reads `width`/`height` from the header into `File::$metadata`. `Srcset` uses them, so a 300 px source is not announced as 800w.
- **GD or Imagick** behind one interface. Imagick applies EXIF orientation and strips metadata. Both check the byte cap and the pixel cap from the header before decoding. Imagick reads only the first frame of an animation: animated GIFs and WebP no longer decode all their frames, which was a DoS through any group with a preset.
- **PDF previews** of the first page, through Imagick and ghostscript. The second review pass found that ImageMagick's ping reads the page box from the raw text and misses an indirect `/MediaBox`, so a 6000-point page was rendered as letter size at 150 DPI and the worker died. Now ghostscript renders onto a fixed media of the pinged size, and a larger raster is refused.
- **Failures are remembered** when you bind a PSR-16 cache: a file that does not decode is not decoded again on every request for 5 minutes. Only verdicts about the bytes are remembered. A missing original or ImageMagick running out of resources under load is never cached, and a cache that throws (Redis is down) is a miss, not a 500.
- **SVG sanitizer** for uploads: `enshrined/svg-sanitize` with remote references removed, plus a byte cap before parsing, removal of `foreignObject` and animation elements, and an element-count cap. Even after sanitizing, serve SVG as an attachment.

One limitation: renditions need a store that implements `DerivativeAwareStoreInterface`. The local stores do; `FlysystemStore` does not, because it cannot enforce a byte cap in the middle of a remote write. Keep image groups on a filesystem store. Before 0.9 the README promised otherwise; that was one of the review's A findings.

## Attachments: -attachments

[`yii3-filestorage-attachments`](/packages/yii3-filestorage-attachments) links files to owners without Active Record: an order's invoice, a product's photos.

```php
$attachments->attach(file: $file, ownerType: 'order', ownerId: (string) $orderId, role: 'invoice');

$invoices = $attachments->forOwner(ownerType: 'order', ownerId: (string) $orderId, role: 'invoice');

// "exactly one invoice per order", in one transaction
$result = $attachments->sync(files: [$newInvoice], ownerType: 'order', ownerId: (string) $orderId, role: 'invoice');
```

`attach()` is idempotent. `detachOwner()` removes all links of a deleted owner. The table has a real foreign key to `filestorage_file`, so deleting a file removes its links. Links are tenant-scoped through the same provider as `-db`, and since 0.6 owners `aB` and `Ab` on MySQL are two owners, not one.

## Console commands

| Command | Package | What it does |
|---|---|---|
| `filestorage:check` | core | wiring, layouts, tenancy, group rules; fails on unsafe combinations |
| `filestorage:stat` | core | counts and sizes per group, and how much sharing saved |
| `filestorage:verify` | core | rows whose object is missing; `--deep` re-reads and compares the hash |
| `filestorage:backfill-hash` | core | fills `contentHash` for old rows |
| `filestorage:gc` | core | collects blobs; `--orphans` sweeps objects with no row and `.part` leftovers |
| `filestorage:import <dir>` | core | imports a directory tree through the ordinary `add()`, with a manifest so a second run is safe |
| `filestorage:deduplicate` | -db | moves existing rows to content keys |
| `filestorage:warm` | -images | pre-generates presets |

`check`, `stat`, `verify` and `gc` take `--format=json`: stdout becomes one object for a dashboard or a cron wrapper. Long commands page by id or by path and print where they stopped, so a large table is a series of bounded runs.

For your own tests the core ships doubles in `src/`, so they are actually installed: `InMemoryStore`, `UrlCapableInMemoryStore` (to exercise the `urlFor()` fallback ladder), `MemoryRepository` and `MemoryBlobLedger`, the dedup state machine in an array.

## How it was checked

### Two review passes before 1.0

On 27 November I ran a read-only review of the whole family before 1.0: four reports, each covering part of the family, across ten areas from bugs and security to test honesty and CI. As with everything in the monorepo, Claude Code agents did the reading, the probes and the fixes; I made the decisions where it came down to a choice. The first pass found 72 issues: 9 of grade A (wrong result, data loss, a bypassed check, a documented guarantee not kept), 32 of grade B and 31 of grade C. The second pass reviewed the fixes themselves and found 47 more: 5 A, 16 B, 26 C.

The second pass is the reason for doing two. Several of its findings were regressions or incomplete fixes from the first wave: the GIF bomb next to the fixed JPEG one, the PAD SPACE collation next to the fixed case-insensitive one, animated WebP broken by the fix for animated GIF, the PDF page box. All 119 are closed in this release: fixed, or documented and closed with a reason. Most A findings were reproduced before the fix with a crafted file or on a live MySQL 8.4; others were checked on MariaDB 11.8 and PostgreSQL 17.

One bug was found by CI rather than by the review: on Windows `FileSystemStore` with `ownedPrefixes` listed nothing, because `realpath()` answers with backslashes and the symlink guard compared that with a `/` path. So `gc --orphans` saw no objects there.

## How to start

Local disk, metadata in a database, signed links:

```bash
composer require rasuvaeff/yii3-filestorage rasuvaeff/yii3-filestorage-db rasuvaeff/yii3-filestorage-web
```

Bind `FileSystemStore` (the recipe above), register the `-db` migrations, run `./yii migrate:up` and `./yii filestorage:check`, and add a signing key of at least 32 bytes in the `-web` params.

Thumbnails: add `-images`, a mutex driver for the lock and, optionally, a PSR-16 cache for failures:

```bash
composer require rasuvaeff/yii3-filestorage-images yiisoft/mutex-file
```

S3: add `-flysystem` and an adapter, and bind `FilesystemOperator` and `TemporaryUrlOptionsInterface => S3TemporaryUrlOptions`. Image groups stay on a local store.

```bash
composer require rasuvaeff/yii3-filestorage-flysystem league/flysystem-aws-s3-v3
```

Deduplication: rebind `StorageInterface` to `DeduplicatingStorageFactory::create()`, then for existing data run `filestorage:deduplicate --apply` and `filestorage:gc --orphans --apply`.

Each package's README covers its part in full, and the core README has the wiring of the whole family in one place. If you are working with an AI assistant, every package has an `llms.txt` and an agent skill.
