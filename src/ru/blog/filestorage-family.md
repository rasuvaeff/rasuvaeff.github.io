Почти любое веб-приложение хранит файлы, которые загружают люди: аватары, счета, фотографии к новости, картинку, вставленную в редактор. И почти каждое делает это на скорую руку: `move_uploaded_file()` в `public/uploads`, расширение от клиента, путь в какой-нибудь текстовой колонке. Это работает, пока кто-нибудь не загрузит HTML-файл или JPEG размером 60000×60000. Или пока скрипт очистки не удалит картинку, на которую ссылается одна забытая страница.

[yii3-filestorage](/ru/packages/yii3-filestorage) — мой ответ для Yii3. Это семейство из шести пакетов, и 28 ноября 2026 года все шесть вышли вместе после двухпроходного ревью перед 1.0. В этом посте описано всё, что умеет семейство, и зачем нужна каждая часть. Цифры — на 28 ноября 2026 года.

## Через что проходит файл

Между «браузер прислал файл» и «он больше никому не нужен» файл проходит несколько этапов, и на каждом что-то может пойти не так:

| Этап | Что может пойти не так |
|---|---|
| Приём | клиент врёт о типе; маленький файл разворачивается в гигабайты пикселей; в имени файла управляющие символы |
| Хранение | путь собран из пользовательского ввода; читатель видит недописанный файл; сегодня локальный диск, завтра S3 |
| Описание | где лежат метаданные; какому арендатору принадлежит файл |
| Выдача | HTML или SVG, отданный inline с вашего домена, — хранимый XSS; приватному файлу нужна ссылка с истечением; видео нужен `Range` |
| Производные | миниатюры произвольного размера из URL; одну и ту же миниатюру генерируют 50 запросов сразу |
| Общие байты | два человека загрузили одни и те же байты, и удаление одного файла не должно удалить другой |
| Удаление | на файл ещё ссылается какой-то текст; ошибочную очистку нельзя откатить |

Семейство закрывает все эти этапы. Ставить нужно только те части, которые вам нужны.

## Архитектура: фасад и две сменные половины

Ядро — один фасад, `StorageInterface`, с методами `add()`, `find()`, `remove()`, `stream()` и `urlFor()`. За ним два контракта:

- `StoreInterface` — где лежат байты: локальный каталог, бакет.
- `RepositoryInterface` — где лежат метаданные: на практике таблица в базе.

**Ядро не привязывает ни один из них.** Какой диск и какая база — решение вашего развёртывания, а `yiisoft/config` разрешает определить DI-ключ только одному vendor-пакету. Если бы ядро привязало хранилище по умолчанию, а `-flysystem` своё, конфигурация упала бы с `Duplicate key`. Поэтому ядро привязывает фасад и свои сервисы, `-db` — репозиторий и реестр, `-flysystem` — хранилище, `-web` — подписчик и генератор ссылок, `-images` — пресеты и процессор. Каждый пакет владеет только своими ключами, поэтому любая комбинация из шести собирается без конфликтов. Проверяю я это харнессом: он ставит всё семейство в одноразовое приложение и мержит конфигурацию так же, как это делает раннер Yii3.

Фасад — обычный интерфейс с `final`-реализацией, поэтому квоты, метрики или антивирус — это декораторы, которые вы пишете сами, а не пакеты, которые ставите. Ядро привязывает фасад под двумя id: `Storage::class` его собирает, а `StorageInterface::class` — алиас на него. Декоратор, привязанный к интерфейсу, берёт `Storage::class`. Если бы он попросил интерфейс, контейнер отдал бы ему его самого и ответил `CircularReferenceException`.

```php
// config/common/di/filestorage.php
use Rasuvaeff\Yii3Filestorage\Storage;
use Rasuvaeff\Yii3Filestorage\StorageInterface;

return [
    StorageInterface::class => static fn (Storage $inner, Quotas $quotas): StorageInterface
        => new QuotaStorage($inner, $quotas),
];
```

## С чего начать: локальный диск

Минимальная рабочая сборка — одна привязка хранилища. Репозиторий даёт `-db`; чтобы попробовать, в ядре есть `Test\MemoryRepository`, который забывает всё по завершении процесса.

```php
// config/common/di/filestorage.php
use Psr\Http\Message\StreamFactoryInterface;
use Rasuvaeff\Yii3Filestorage\Store\FileSystem\FileSystemStore;
use Rasuvaeff\Yii3Filestorage\Store\StoreInterface;

return [
    StoreInterface::class => static fn (StreamFactoryInterface $streams): StoreInterface
        => new FileSystemStore(
            name: 'upload',
            rootPath: '/app/runtime/upload',
            streamFactory: $streams,
            quarantinePath: '/app/runtime/upload-quarantine', // куда gc уносит удаляемое
        ),
];
```

Дальше `./yii filestorage:check` показывает сборку, раскладку и возможности каждого хранилища, режим арендаторов и правила каждой группы, и падает на небезопасных сочетаниях. О них ниже.

## Сохранение и чтение

Файл может прийти из четырёх мест, и каждое превращается в `Upload`:

```php
$file = $storage->add(
    Upload::fromUploadedFile($request->getUploadedFiles()['avatar'], $streamFactory),
    groupName: 'avatars',
);

$file = $storage->add(
    Upload::fromStream($pdfStream, 'invoice-2026-08.pdf', $streamFactory), // сгенерированный PDF
    groupName: 'documents',
    metadata: ['invoiceId' => 4711],
);

$file = $storage->add(Upload::fromPath('/tmp/import.csv', $streamFactory));

$file = $storage->add(Upload::fromDataUrl( // редакторы, JSON API
    'data:image/png;base64,' . $base64Payload,
    'logo.png',
    $streamFactory,
    $clientHint,
    maxSpoolBytes: 5_242_880,
));
```

`Upload` один раз нормализует имя файла от клиента: убирает управляющие и bidi-символы (U+202E превращает `invoice<U+202E>gpj.exe` в видимое `invoiceexe.jpg`), заменяет невалидный UTF-8 и обрезает имя до 255 символов, сохраняя расширение. Имя остаётся метаданными и никогда не попадает в путь. Тело без перемотки копируется во временный буфер с лимитом, чтобы определение типа, политика, хеш и запись читали один и тот же вход.

Результат — неизменяемый `File`: id (по умолчанию UUIDv7), хранилище, группа, путь, исходное имя, определённый тип, размер, описание, хеш, метаданные и метки времени. Чтение — `stream()` (PSR-7, основной путь), `content()` (с лимитом `maxInlineBytes`, по умолчанию 8 МиБ) и `exists()`. Метаданные меняются через `File::withMetadata()` и `save()`, и новая метка времени здесь важна: `updatedAt` входит в валидатор скачивания.

Каждый `add()` — всё или ничего: либо строка с объектом, либо ничего. Всё, что передал вызывающий код, проверяется до записи. Сбой после записи — это `AddException`, и записанный объект удаляется. `addMany()` нет намеренно: пакет нельзя сделать атомарным поверх файловой системы или объектного хранилища, а метод с таким именем обещал бы атомарность.

## Безопасный приём файлов

### Группы и политики

Группа — это сценарий, а не папка. Правила задаются один раз в `params`, а не проверяются перед каждым `add()`:

```php
// config/common/params.php
return [
    'rasuvaeff/yii3-filestorage' => [
        'policies' => [
            'avatars' => [
                'allowedMimeTypes' => ['image/jpeg', 'image/png', 'image/webp'],
                'maxBytes' => 5_242_880,
                'maxPixels' => 40_000_000,
                'requireImageDimensions' => true,
            ],
            'documents' => ['allowedMimeTypes' => ['application/pdf'], 'maxBytes' => 52_428_800],
            '*' => ['maxBytes' => 20_971_520],
        ],
        'delivery' => [
            '*' => ['allowDirectPublicUrl' => false, 'forceDownload' => true],
        ],
    ],
];
```

Отклонённая загрузка бросает исключение до того, как тронуто хранилище, и исключения ложатся на HTTP-статусы:

```php
try {
    $file = $storage->add($upload, groupName: 'avatars');
} catch (SizeLimitExceededException) {
    // 413: maxBytes, лимит буфера, data URL сверх лимита, upload_max_filesize
} catch (UnsupportedMediaTypeException $e) {
    // 415
} catch (PolicyViolationException $e) {
    // 400/422: лимит пикселей, неизмеримое изображение
}
```

В локальных хранилищах `maxBytes` проверяется **во время копирования**, а не после: тело неизвестной длины останавливается, как только пересекает лимит, а недописанный объект удаляется.

### Тип определяется по содержимому

Считается только ответ `finfo`. Тип, присланный клиентом, хранится для диагностики и никогда не попадает ни в политику, ни в путь, ни в заголовок `Content-Type`. Расширение файла берётся из определённого типа по таблице `symfony/mime`. Исполняемые в браузере типы (HTML, SVG, XML и любой `+xml`, JavaScript) и типы с исполняемым расширением хранятся как `.bin`, если вы явно не вернули расширение через `extensionOverrides`.

### Декомпрессионные бомбы

`maxPixels` (по умолчанию 40 миллионов) читается из заголовка изображения, пиксели не декодируются никогда. Ревью показало, что фиксированного окна заголовка мало, поэтому каждый формат обходится по-своему:

- **JPEG** обходится маркер за маркером до заголовка кадра. До 0.10 файл в 325 КБ размером 60000×60000 проходил любую политику: набивка APPn отодвигала заголовок кадра за первые 256 КиБ, а «размеры не найдены» означало «пропустить проверку». Второй заголовок кадра перед сканом тоже отклоняется.
- **GIF** обходится блок за блоком. `getimagesize()` сообщает размер логического экрана, а декодер выделяет память под каждый кадр по его собственному размеру. Поэтому файл в 47 КБ с экраном 1×1 вокруг кадра 8000×8000 проходил проверку. Теперь кадр, который не помещается в экран, отклоняется.
- **TIFF** измеряется по цепочке каталогов, где бы её ни разместил кодировщик.

JPEG, PNG, GIF, WebP или TIFF, размеры которого установить не удалось, **отклоняется**. Остальные растровые форматы (AVIF, HEIC…) измеряются по первым 256 КиБ, и `requireImageDimensions` отклоняет их, если размер там не нашёлся.

### Активное содержимое

У семейства один список активных типов, `Mime\ActiveMediaTypes`, в одном настроенном экземпляре. В нём два уровня: исполняемые в браузере типы (HTML, XHTML, SVG, XML и любой `+xml`, XSLT, MathML, JavaScript, RSS/Atom) и типы плагинов (PDF, Flash). Что бы ни говорила политика группы, всё из этого списка отдаётся как вложение: через прокси, через подписанную ссылку S3, везде. `filestorage:check` падает, если группа с прямыми публичными ссылками принимает исполняемые типы. `activeMediaTypes.extra` добавляет типы, а `allowInline` выпускает типы плагинов, чтобы PDF можно было показать inline. Исполняемый тип выпустить нельзя.

До 0.10 списков было два: 10 типов в `-web` и 5 в `check`, и подписанная ссылка S3 отдавала SVG inline. Теперь список один.

Две вещи ядро за вас не делает и честно об этом пишет. EXIF с GPS-координатами остаётся в оригинале (в примерах `-images` есть декоратор, который перекодирует загрузку). SVG, отданный с вашего домена, — это программа. Для SVG в `-images` есть очистка, которую включают явно.

## Ссылки: публичные, подписанные, через прокси

Вызывать нужно один метод: `$storage->urlFor($file)`. Он применяет политику выдачи группы и пробует по порядку:

1. постоянную публичную ссылку, но **только** если группа явно её разрешает;
2. подписанную ссылку самого хранилища (S3 через `-flysystem`);
3. подписанную ссылку на прокси приложения (`-web`).

Подписанная ссылка S3 идёт мимо приложения, поэтому заголовки, которые добавит S3, и становятся ответом. Если ссылка не может унести disposition и тип, которых требует политика, хранилище не возвращает ссылку, и вызов переходит к прокси, который ставит заголовки сам. Шаблонам не нужно разбираться, публичное ли сейчас хранилище.

### Прокси в -web

[`yii3-filestorage-web`](/ru/packages/yii3-filestorage-web) выпускает токены замороженного формата `v1.<key-id>.<expires>.<payload>.<hmac>`: HMAC-SHA256 над всем, что до подписи. В payload — id файла, вариант и арендатор. Достаточно поставить пакет: `urlFor()` начинает возвращать подписанные ссылки для приватных хранилищ.

```php
// config/common/routes.php
use Rasuvaeff\Yii3FilestorageWeb\Action\FileDownloadAction;
use Yiisoft\Router\Route;

return [
    Route::get('/files/{token}')->action(FileDownloadAction::class)->name('file/download'),
];
```

Что гарантирует экшен скачивания:

| Правило | Зачем |
|---|---|
| Любой сбой — 404: неверная подпись, истёкший токен, чужой арендатор, пропавшие байты | 403 подтвердил бы, что такой id существует |
| Арендатор берётся из токена, а не из запроса | подписанная ссылка работает без сессии, а утёкший id в другом арендаторе ничего не находит |
| Условные запросы отвечаются до открытия хранилища | `304` стоит одного чтения метаданных; ради него миниатюра не генерируется |
| `If-Modified-Since` подтверждает только inline-ответ | `ETag` несёт disposition, а дата нет; иначе закешированная inline-копия переживёт переход на `forceDownload` |
| Активное содержимое — вложение, с `nosniff` | хранимый XSS с вашего же домена |
| По токену миниатюры оригинал не отдаётся | вариант входит в подпись |

Диапазоны отдаются там, где они дёшевы, а это вопрос к хранилищу. Хранилище с чтением по диапазону получает одно такое чтение, локальный файл с перемоткой режется через seek, а для потока S3 без перемотки честно отдаётся полный `200` без `Accept-Ranges`. Один диапазон даёт `206`, запрос за пределами файла — `416`, а `If-Range` начинает скачивание заново, если файл изменился, вместо того чтобы склеить два разных файла.

Ключи подписи ротируются без поломки ссылок, которые уже лежат во входящих, потому что id ключа входит в подписанный конверт. У ссылки, выпущенной вне запроса (письмо из очереди, отчёт), нет текущего арендатора; `forScope()` у `HmacProxyUrlGenerator` ставит его явно (`withProxyUrls()` есть у конкретного `Storage` и у `DeduplicatingStorage` из `-db`, а не у `StorageInterface`):

```php
$url = $storage->withProxyUrls($proxyUrls->forScope($tenantId))->urlFor($file);
```

Вторая половина `-web` — `FileUploadAction`: один файл на запрос (мультизагрузку тоже нельзя сделать атомарной), `201` с JSON, `413`, `415`, `400`, `500` для ошибок, которые клиент не исправит. `Validation\FileRule` повторяет проверки на уровне формы для `yiisoft/validator`, чтобы ошибка появилась рядом с полем, а решающие проверки всё равно выполняются в `add()`.

## Как файлы лежат на диске

### Две раскладки

`DirectoryLayout` — замороженное умолчание: у каждого файла свой каталог, `<…>/<key>/original.<ext>`, а `delete()` удаляет каталог. Поэтому миниатюра может лежать в `<key>/thumb-v1.webp` без изменения схемы, и удаление файла никогда не оставляет его производные.

`FlatSiblingLayout` выбирается один раз на хранилище, пока в нём нет данных. Она для плоских деревьев по содержимому вроде `blobs/ab/cd/<sha>.<ext>`, где производные лежат рядом с оригиналом как `<sha>-thumb-v1.webp`. `FlatSha256KeyGenerator(prefix: 'blobs')` подхватывает существующее дерево такой формы как есть. Его ключи не учитывают арендатора, так что он для установки с одним арендатором.

### Пара должна совпадать

Самая тяжёлая находка первого прохода была здесь. Генератор ключей и раскладка настраиваются в двух разных местах, и плоский ключ под `DirectoryLayout` превращал удаление одного блоба в удаление всего каталога `ab/cd/` вместе со всеми соседями, у которых совпадают первые четыре hex-цифры. Это независимо нашли три отчёта из четырёх. Теперь `DirectoryLayout` отказывается работать с файлом, который называется не `original[.<ext>]`, а `LayoutCompatibility` проверяет пару по поведению: берёт два ключа из одного каталога и спрашивает раскладку, что удалит удаление каждого. Её вызывают фабрика `-db`, DI `-flysystem` и `filestorage:check`.

### Публичный каталог, общий с приложением

В публичном каталоге обычно лежат и собственные файлы приложения. `gc --orphans` считает сиротой всё под корнем хранилища, на что нет строки, поэтому корень принадлежит хранилищу. Скрытые записи (`.htaccess`, `.well-known/`) не перечисляются никогда, а `ownedPrefixes` ограничивает инвентарь собственными поддеревьями хранилища и запрещает запись вне их. `webRoot` позволяет `PublicFileSystemStore` отказаться от карантина внутри корня сайта.

```php
$store = new PublicFileSystemStore(
    new FileSystemStore(
        name: 'uploads',
        rootPath: '/app/public/uploads',
        streamFactory: $streams,
        quarantinePath: '/app/runtime/uploads-quarantine',
        layout: new FlatSiblingLayout(),
        ownedPrefixes: ['blobs', 'files'],
    ),
    baseUrl: '/uploads',
    webRoot: '/app/public',
);
```

С 0.10 оба локальных хранилища адресуются по содержимому: пишут под случайным именем `.part` и публикуют через `link()`, который отказывается перезаписывать существующий файл. Два писателя одних и тех же байтов оба завершаются успешно, и дедупликация теперь работает и на локальном диске, публичном или нет. Одно честное предупреждение из README: в публичном хранилище ключ по содержимому — это SHA-256 байтов, и любой, у кого есть те же байты, может вычислить URL. Приватные группы в публичное хранилище с ключами по содержимому не кладите.

## Метаданные в базе: -db

[`yii3-filestorage-db`](/ru/packages/yii3-filestorage-db) хранит строки в трёх таблицах: `filestorage_file`, `filestorage_blob` и `filestorage_blob_reservation`. Миграции регистрируются по namespace и требуют `yiisoft/db-migration` ^2.1: на 2.0 такая регистрация молча ничего не находила, и `migrate:up` завершался с кодом 0, не создав ни одной таблицы. Интеграционный сьют исполняет этот рецепт на каждой сборке.

### Арендаторы

Привяжите `FileScopeProviderInterface`, и каждый запрос пакета получит предикат по `scope_id`. Метода, который пропускает его для определённого арендатора, нет. У подписанного скачивания нет текущего арендатора, и все тянутся к одному решению — выключить фильтр для скачиваний. Это межарендаторное чтение любого файла, id которого утёк. Вместо этого арендатор едет внутри HMAC, и `ScopedFileResolverInterface` сверяет его вторым предикатом.

В 0.4 изменились три вещи:

- **Провайдер, вернувший `null`, получает отказ.** Раньше арендатор, который не определился (анонимный маршрут, задача без контекста), снимал предикат целиком, и `find()` видел строки всех арендаторов. Теперь это `MissingScopeException`.
- **Глобальный доступ — явная опция для обслуживания**, `globalMaintenanceAccess`. Она действует только на два ключа, которые берут команды обслуживания, поэтому воркер очереди с теми же консольными params по-прежнему получает отказ.
- **Арендаторы сравниваются побайтово и на MySQL с MariaDB.** Их коллации по умолчанию считают `Acme`, `acme` и `Acmé` одним арендатором. Миграция переводит колонку на бинарную NO PAD-коллацию (`utf8mb4_0900_bin` или `utf8mb4_nopad_bin`). Первое исправление взяло `utf8mb4_bin`, а это PAD SPACE: второй проход ревью нашёл, что `acme ` и `acme` стали одним арендатором — такого совпадения MySQL 8 по умолчанию никогда не давал.

## Дедупликация

Два человека загрузили один и тот же файл. Один объект на диске, две строки, и объект не должен исчезнуть, когда удалят первую строку. Владение — физический `BlobId` (один объект в одном хранилище), а не хеш: хеш одинаков во всех хранилищах, группах и арендаторах, и счётчик по хешу позволит одному арендатору удалить то, что читает другой. Колонки `reference_count` тоже нет: ссылка — это и есть строка файла, указывающая на блоб, а защиты спрашивают `NOT EXISTS`.

Протокол — резерв, публикация, фиксация:

```php
$blob = BlobId::create('upload', $contentAddressedPath);

$reservation = $ledger->reserve($blob, $sha256, $size, $expiresAt); // занять ключ
$store->putIfAbsent($upload, $blob->object);                         // опубликовать байты
$ledger->commit($reservation, $file);                                // строка + ссылка, одна транзакция
```

Правило, на котором держится вся конструкция: **общие байты никогда не удаляются внутри запроса.** Последнее освобождение только помечает блоб `pending_delete`. Удаляет только сборщик, только под исключительной арендой с истечением и только пока счётчики ссылок и резервов равны нулю в том же запросе, который забирает блоб. `SELECT`, а потом `UPDATE` — это два момента с зазором, и в этом зазоре зафиксированная строка начинает указывать на удалённые байты.

Вручную протокол вести не нужно. Дедупликация включается перепривязкой фасада:

```php
// config/common/di/filestorage.php
use Rasuvaeff\Yii3Filestorage\StorageInterface;
use Rasuvaeff\Yii3FilestorageDb\DedupScope;
use Rasuvaeff\Yii3FilestorageDb\DeduplicatingStorageFactory;

return [
    StorageInterface::class => static fn (DeduplicatingStorageFactory $factory): StorageInterface
        => $factory->create(
            scope: DedupScope::TenantGroup,
            dedupMaxBytes: 104_857_600,
            deleteGracePeriod: new DateInterval('PT1H'),
        ),
];
```

`DedupScope` — выбор безопасности, а не ручка экономии места: `TenantGroup` (по умолчанию, безопасен для недоверенных арендаторов), `Tenant` или `Global`, который экономит больше всего и показывает между арендаторами, существовал ли уже такой файл (это видно и по времени записи, и по квоте, которая не сдвинулась). Фабрика отказывается от пяти конфигураций, которые тихо теряли бы данные: хранилище без адресации по содержимому, реестр не `DbBlobLedger`, реестр на другом соединении, чем репозиторий (тогда `commit()` — две транзакции), ключи, которые раскладка не умеет удалять по одному, и, при арендаторах, генератор, который не включает арендатора в ключ.

Файлы больше `dedupMaxBytes` молча идут уникальным путём: ключ — это хеш, и чтобы его выбрать, надо сначала прочитать всё тело.

На MySQL реестр выполняет свои транзакции на `READ COMMITTED`. Под REPEATABLE READ MariaDB 11.6.2+ с `innodb_snapshot_isolation` (включён по умолчанию) роняет чтение-затем-обновление с ошибкой 1020, если другое соединение успело изменить строку, например когда два человека загружают один файл в одну секунду. MySQL так не делает никогда, поэтому это увидела только MariaDB-нога CI.

Существующие данные переносит `filestorage:deduplicate`. Он читает каждую строку, хеширует её, публикует через `putIfAbsent()` и перенаправляет строку тем же `commit()`. После сбоя остаётся либо старая строка, либо новая. Старый объект остаётся на месте намеренно: его путь может держать читатель, а `gc --orphans` заберёт его позже.

## Удаление: двухфазная сборка мусора

`filestorage:gc` — единственное место в семействе, которое удаляет байты, нужные, возможно, другому запросу. С 0.9 он никогда не удаляет сразу:

1. байты переносятся в **карантин** хранилища, вне корня и вне всего, что отдаёт веб-сервер;
2. решение фиксируется в реестре;
3. только потом байты стираются или, если фиксация отклонена, возвращаются по принципу «положить, если нет».

Раньше сборщик, простоявший дольше своей аренды, удалял байты, которые писатель за это время опубликовал заново. Теперь его фиксация отклоняется, и байты возвращаются.

| Правило | Что защищает |
|---|---|
| Сирота — кандидат только после `--min-age` (1 час), отсчитанного после перечисления её страницы; объект без метки времени — никогда | загрузки между публикацией байтов и сохранением строки; для `--orphans --apply` больше не нужно останавливать загрузки |
| Сироты и освобождённые файлы лежат в карантине `--retention` (7 дней) | ошибочную очистку можно откатить в течение недели |
| Каждая запись карантина на каждом прогоне сверяется со строками и проверкой ссылок | файл, на который снова сослались, возвращается сразу |
| Одна сбойная запись пропускается и считается, прогон не останавливается | раньше одна сломанная запись стопорила весь карантин на каждом прогоне |
| Файлы `.part` от упавших записей удаляются по возрасту | раньше их не собирал никто, а публичный корень их отдавал |
| `gc --orphans` отказывается работать при привязанном провайдере арендаторов | строки одного арендатора не доказывают, что на объект никто не ссылается; очистка удалила бы файлы всех остальных |

`gc`, `backfill-hash` и `deduplicate` по умолчанию только показывают отчёт и действуют лишь с `--apply`. Команду, которая удаляет с первого запуска, однажды кто-нибудь запустит не на той базе.

### Когда ссылки — это URL внутри текста

По умолчанию ссылка — это сама строка: файл живёт, пока приложение не удалит строку. Но многие приложения ссылаются на файлы URL-ами внутри HTML, Markdown или JSON. Для таких групп ставится `'referencesOwnedBy' => 'application'` и привязывается `ReferenceCheckerInterface`, который постранично, пачкой, отвечает, какие пути ещё упоминаются:

```php
final readonly class TextColumnReferences implements ReferenceCheckerInterface
{
    public function referenced(string $storeName, array $objects): array
    {
        return array_values(array_filter(
            $objects,
            fn (StoredObjectId $object): bool => $this->index->mentions($object->relativePath),
        ));
    }
}
```

Тогда `gc` освобождает строки старше `--min-age`, которых проверка больше не называет, и переспрашивает её прямо перед тем, как унести блоб в карантин: URL, вставленный обратно за это время, сохраняет свои байты.

Перед выпуском семейство примерили на настоящем приложении — фан-сайте, который работает в проде. Эта примерка добавила в README две ловушки, в которые легко попасть:

- **Пропускайте собственные таблицы пакета.** `filestorage_file.relative_path` называет каждый сохранённый файл. Обход «всех текстовых колонок», который их включает, отвечает «есть ссылка» на каждую строку, и не освобождается ничего.
- **Ищите все формы ссылок, которые пишет приложение.** URL (`/uploads/blobs/…`) и путь внутри хранилища (`blobs/…`, который держит, скажем, колонка кеша картинок) — обе ссылки. Проверка, которая ищет одну форму, освободит файлы, на которые всё ещё указывает другая.

## Объектные хранилища: -flysystem

[`yii3-filestorage-flysystem`](/ru/packages/yii3-filestorage-flysystem) — один класс `FlysystemStore` на все адаптеры. Адаптеры действительно разные, а PHP-интерфейс нельзя реализовать по условию во время выполнения, поэтому хранилище сообщает свои возможности результатами, а не интерфейсами. Ссылки реализованы всегда и возвращают `null`, если адаптер не умеет их выпускать. `Range` нет: `readStream()` возвращает объект целиком, а поток S3 не перематывается, и притворство превратило бы «перемотать на последнюю минуту» в полное скачивание. Для S3 подписанная ссылка сама поддерживает диапазоны.

Подписанные ссылки выпускаются только через явное отображение `S3TemporaryUrlOptions`, которое вшивает в ссылку `ResponseContentType` и `ResponseContentDisposition`. Без отображения подписанных ссылок нет, и файл отдаёт прокси. Активные типы подписываются как `attachment`, потому что ответ S3 не может нести `nosniff`. Сохранённый тип, который не соответствует грамматике RFC 9110, подписывается как `application/octet-stream`: простое удаление CR/LF склеивало `image/svg+xml\r\nX: y` в `image/svg+xmlX: y` — тип, которого нет ни в одном списке.

Что ещё в пакете:

- **Один листинг на проход `gc`.** В 0.4 каждая страница листала бакет с начала: на 10 000 объектов без `orderedListing` — 425 397 полученных записей. Теперь страница продолжает листинг предыдущей.
- **`orderedListing` проверяется, а не принимается на веру.** Ошибочно объявленный порядок молча терял объекты: проба увидела 1 067 из 10 000. Теперь сравнивается каждая соседняя пара, и первый ключ не по порядку останавливает проход с ошибкой.
- **Карантин** лежит под префиксом, который начинается с `.` или `_`, и перенос в него идёт с `ACL: private`. Иначе копирование S3 во Flysystem сохраняет публичный ACL, и удалённый публичный объект остаётся доступным весь срок хранения.
- **`publicBucket`** — ваше заявление, что бакет отдаёт объекты без учётных данных. Тогда `check` валит каждую группу, принимающую активное содержимое. Хранилище не угадывает это само: S3-адаптер строит URL объекта и для приватного бакета.
- **Лимиты размера.** Удалённый `PUT` нельзя прервать посередине, поэтому лимит проверяется до записи и сверяется после неё, а объект, занизивший свой размер, удаляется.
- **Дедупликация** — только через `FlysystemContentAddressableStore` с явным `AdapterSemantics`: атомарная видимость и неизменяемые ключи по содержимому. Разрешающего умолчания нет. Без этих гарантий `fileExists()`, а затем `write()` отдаст второму писателю недозагруженный объект и назовёт это попаданием в кеш.

```php
return [
    StoreInterface::class => static fn (
        FilesystemOperator $filesystem,
        StreamFactoryInterface $streams,
        ActiveMediaTypes $activeTypes,
    ): StoreInterface => new FlysystemContentAddressableStore(
        store: new FlysystemStore(
            name: 's3',
            filesystem: $filesystem,
            streamFactory: $streams,
            temporaryUrlOptions: new S3TemporaryUrlOptions($activeTypes),
            quarantinePrefix: '.quarantine',
            orderedListing: true,
        ),
        semantics: AdapterSemantics::guaranteed(),
    ),
];
```

Интеграционный сьют гоняется на SeaweedFS, настоящем S3-шлюзе: образы MinIO в сентябре пропали с Docker Hub.

## Изображения: -images

[`yii3-filestorage-images`](/ru/packages/yii3-filestorage-images) делает производные **только по именованным пресетам**. `w=200&h=200` в URL, даже подписанном, превращает одну загрузку в бесконечный набор адресуемых производных; белый список делает этот набор конечным.

```php
// config/common/params.php
return [
    'rasuvaeff/yii3-filestorage-images' => [
        'presets' => [
            'thumb' => ['version' => 1, 'width' => 200, 'height' => 200, 'fit' => 'cover', 'format' => 'webp', 'quality' => 82],
            'poster' => ['width' => 1280, 'format' => 'jpeg'],
        ],
    ],
];
```

```php
$url = $derivatives->urlFor($file, 'thumb');
$srcset = Srcset::for($derivatives, $presets, $file, ['thumb', 'poster']); // "url 200w, url 1280w"
```

- **Версия — часть имени** (`thumb-v2.webp`). Если поменять настройки пресета под тем же именем, продолжат отдаваться старые миниатюры; увеличение `version` создаёт новый объект.
- **Лениво, под блокировкой от наплыва.** Первый запрос генерирует производную, все следующие её читают. Блокировка привязана к физической производной, поэтому при дедупликации запросы к разным строкам с общим объектом всё равно генерируют один раз. `filestorage:warm` заранее генерирует через тот же путь с блокировкой.
- **Размеры при загрузке.** `ImageMetadataStorage` записывает `width`/`height` из заголовка в `File::$metadata`. Их использует `Srcset`, поэтому источник в 300 пикселей не объявляется как 800w.
- **GD или Imagick** за одним интерфейсом. Imagick учитывает EXIF-ориентацию и вырезает метаданные. Оба проверяют лимит байтов и лимит пикселей по заголовку до декодирования. Imagick читает только первый кадр анимации: анимированные GIF и WebP больше не декодируют все свои кадры — раньше это был DoS через любую группу с пресетом.
- **Превью PDF** по первой странице, через Imagick и ghostscript. Второй проход ревью нашёл, что ping в ImageMagick читает размер страницы из сырого текста и не видит косвенный `/MediaBox`: страница в 6000 пунктов определялась как letter, рендерилась на 150 DPI, и воркер падал. Теперь ghostscript рендерит на фиксированный холст измеренного размера, а растр больше него отклоняется.
- **Сбои запоминаются**, если привязан кеш PSR-16: файл, который не декодируется, не декодируется заново на каждый запрос ещё 5 минут. Запоминаются только выводы о самих байтах. Пропавший оригинал или нехватка ресурсов ImageMagick под нагрузкой не кешируются никогда, а кеш, который бросает исключение (Redis лёг), — это промах, а не 500.
- **Очистка SVG** для загрузок: `enshrined/svg-sanitize` без внешних ссылок, плюс лимит байтов до разбора, удаление `foreignObject` и элементов анимации и лимит числа элементов. Даже очищенный SVG отдавайте вложением.

Одно ограничение: производным нужно хранилище с `DerivativeAwareStoreInterface`. Локальные хранилища его реализуют, `FlysystemStore` — нет, потому что не может удержать лимит размера посреди удалённой записи. Группы с картинками держите на файловом хранилище. До 0.9 README обещал обратное, и это была одна из находок класса A.

## Вложения: -attachments

[`yii3-filestorage-attachments`](/ru/packages/yii3-filestorage-attachments) связывает файлы с владельцами без Active Record: счёт заказа, фотографии товара.

```php
$attachments->attach(file: $file, ownerType: 'order', ownerId: (string) $orderId, role: 'invoice');

$invoices = $attachments->forOwner(ownerType: 'order', ownerId: (string) $orderId, role: 'invoice');

// «ровно один счёт на заказ», в одной транзакции
$result = $attachments->sync(files: [$newInvoice], ownerType: 'order', ownerId: (string) $orderId, role: 'invoice');
```

`attach()` идемпотентен. `detachOwner()` удаляет все связи удалённого владельца. У таблицы настоящий внешний ключ на `filestorage_file`, так что удаление файла удаляет и его связи. Связи разделены по арендаторам через тот же провайдер, что и в `-db`, а с 0.6 владельцы `aB` и `Ab` на MySQL — это два владельца, а не один.

## Консольные команды

| Команда | Пакет | Что делает |
|---|---|---|
| `filestorage:check` | ядро | сборка, раскладки, арендаторы, правила групп; падает на небезопасных сочетаниях |
| `filestorage:stat` | ядро | число и объём файлов по группам и сколько сэкономили общие байты |
| `filestorage:verify` | ядро | строки, у которых пропал объект; `--deep` перечитывает и сверяет хеш |
| `filestorage:backfill-hash` | ядро | заполняет `contentHash` у старых строк |
| `filestorage:gc` | ядро | собирает блобы; `--orphans` чистит объекты без строк и остатки `.part` |
| `filestorage:import <dir>` | ядро | импортирует дерево каталогов через обычный `add()`, с манифестом, чтобы повторный запуск был безопасен |
| `filestorage:deduplicate` | -db | переводит существующие строки на ключи по содержимому |
| `filestorage:warm` | -images | заранее генерирует пресеты |

`check`, `stat`, `verify` и `gc` принимают `--format=json`: stdout становится одним объектом для дашборда или обёртки cron. Длинные команды идут страницами по id или по пути и печатают, где остановились, так что большая таблица обрабатывается серией ограниченных прогонов.

Для ваших собственных тестов ядро кладёт двойники в `src/`, чтобы они действительно устанавливались: `InMemoryStore`, `UrlCapableInMemoryStore` (чтобы проверить лестницу `urlFor()`), `MemoryRepository` и `MemoryBlobLedger` — машина состояний дедупликации в массиве.

## Как это проверяли

### Два прохода ревью перед 1.0

27 ноября я провёл ревью всего семейства перед 1.0, только чтением: четыре отчёта, каждый по своей части семейства, по десяти направлениям — от багов и безопасности до честности тестов и CI. Как и всё в монорепо, читали код, писали пробы и исправляли агенты Claude Code; решения там, где всё упиралось в выбор, принимал я. Первый проход нашёл 72 проблемы: 9 класса A (неверный результат, потеря данных, обход проверки, невыполненная документированная гарантия), 32 класса B и 31 класса C. Второй проход проверял сами исправления и нашёл ещё 47: 5 A, 16 B, 26 C.

Второй проход — причина, по которой их было два. Несколько его находок оказались регрессиями или неполными исправлениями первой волны: GIF-бомба рядом с закрытой JPEG-бомбой, коллация PAD SPACE рядом с исправленным сравнением без учёта регистра, анимированный WebP, сломанный исправлением для анимированного GIF, размер страницы PDF. Все 119 закрыты в этом выпуске: исправлены или задокументированы и закрыты с обоснованием. Большинство находок класса A до исправления воспроизвели специально собранным файлом или на живом MySQL 8.4; другие проверяли на MariaDB 11.8 и PostgreSQL 17.

Одну ошибку нашло не ревью, а CI: на Windows `FileSystemStore` с `ownedPrefixes` ничего не перечислял, потому что `realpath()` отвечает с обратными слешами, а защита от симлинков сравнивала это с путём через `/`. В итоге `gc --orphans` не видел там ни одного объекта.

### Тесты и мутации

| Пакет | Тесты | MSI | Порог |
|---|---:|---|---:|
| `yii3-filestorage` | 1 381 | 88,9% | 87 |
| `yii3-filestorage-db` | 391 | 90,7% | 89 |
| `yii3-filestorage-flysystem` | 236 | около 98% на 0.4.0; 0.5 заново не мерили | 88 |
| `yii3-filestorage-web` | 182 | 93% по покрытому коду | 93 |
| `yii3-filestorage-attachments` | 71 | 97,6% | 94 |
| `yii3-filestorage-images` | 334 | 91,2% по покрытому коду; 76% в целом | 83 |
| **Всего** | **2 595** | | |

Мутации гоняются с `--with-uncovered` (мутируется и код, который тесты выполняют, но не называют в `#[Covers]`), кроме `-images`, который на этот флаг ещё не перешёл. Поэтому у него два числа. Часть тестов `-images` пропускается в образе без GD и Imagick; в CI они идут с обоими.

CI гоняет PHP 8.3–8.6 (в `-db`, `-web` и `-attachments` 8.6 пока экспериментальная джоба), самые старые разрешённые версии зависимостей, джобу на Windows, S3-тесты на SeaweedFS и интеграционные сьюты `-db` и `-attachments` на SQLite, MySQL 8.4, MariaDB 11.8 и PostgreSQL 17. Часть тестов на MySQL идёт в режиме `NO_BACKSLASH_ESCAPES`. Этот случай появился из-за находки первого прохода: `LIKE` без `ESCAPE` в этом режиме не находил каталоги с `_` или `%`, и `gc --orphans` уносил в карантин файлы, на которые указывали живые строки.

## С чего начать

Локальный диск, метаданные в базе, подписанные ссылки:

```bash
composer require rasuvaeff/yii3-filestorage rasuvaeff/yii3-filestorage-db rasuvaeff/yii3-filestorage-web
```

Привяжите `FileSystemStore` (рецепт выше), зарегистрируйте миграции `-db`, выполните `./yii migrate:up` и `./yii filestorage:check` и добавьте в params `-web` ключ подписи не короче 32 байтов.

Миниатюры: добавьте `-images`, драйвер мьютекса для блокировки и, по желанию, кеш PSR-16 для сбоев:

```bash
composer require rasuvaeff/yii3-filestorage-images yiisoft/mutex-file
```

S3: добавьте `-flysystem` и адаптер и привяжите `FilesystemOperator` и `TemporaryUrlOptionsInterface => S3TemporaryUrlOptions`. Группы с картинками остаются на локальном хранилище.

```bash
composer require rasuvaeff/yii3-filestorage-flysystem league/flysystem-aws-s3-v3
```

Дедупликация: перепривяжите `StorageInterface` на `DeduplicatingStorageFactory::create()`, а для существующих данных выполните `filestorage:deduplicate --apply` и `filestorage:gc --orphans --apply`.

README каждого пакета описывает его часть целиком, а в README ядра сборка всего семейства собрана в одном месте. Если вы работаете с ИИ-ассистентом, у каждого пакета есть `llms.txt` и скилл для агента.
