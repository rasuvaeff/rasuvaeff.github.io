Каждый гайд про Claude Code за VPN заканчивается одинаково: «убедитесь, что трафик идёт через выход». Никто не рассказывает, что бывает, когда он туда не идёт.

У меня стоит локальный прокси-клиент ([happ](https://github.com/username/happ)), чей туннель падает несколько раз в день. Когда он падает, мой трафик не останавливается — он **переключается на реальный адрес** и продолжает работать. Браузер этого не замечает: keep-alive соединения выживают, страницы грузятся из кеша. Claude Code замечает, потому что открывает новое соединение на каждый запрос — и каждый уходит с моего домашнего адреса.

## Установка

Скопируйте и запустите:

```bash
curl -fsSL https://raw.githubusercontent.com/rasuvaeff/shuang/master/scripts/install.sh | sh
```

Нативная панель, иконка в трее, три платформы. Без сервера, без телеметрии.

## Идея

Решение — пер-приложение kill switch: заморозить процесс в момент, когда выход неправильный, и продолжить, когда вернётся. Не kill-and-restart (сессии умирают), и не файрвол на всю систему (останавливается вообще всё).

Заморозить процесс — один системный вызов (`SIGSTOP` на Unix, `NtSuspendProcess` на Windows). Всё остальное — сложная часть.

## Что реально заняло время

**Корректная проверка выхода.** «Проверь IP» звучит тривиально. На практике: 4 IP-сервиса должны **сойтись** (один врущий сервис не должен открывать gate), IPv6 требует пяти состояний (disabled / confirmed / conflict / required / unavailable), совпадение страны покрывает IPv4, но **не** IPv6, а выход с флагом datacenter нуждается в собственном guard.

**Детектор утечки домашнего IP.** Первая диагностическая сессия нашла то, чего я не ожидал: 145 эпизодов, когда выходом был мой **резидентный адрес** (провайдер моего региона, `proxy: false, hosting: false`). Не вторая нода VPN — мой реальный адрес, утекающий через туннель. shuang теперь называет это явно: событие `home-ip-leak`, критическое уведомление на рабочем столе и замороженное дерево до возвращения туннеля.

**Безопасное восстановление.** «PID 12345 заморожен, продолжи» ломается, когда ОС отдаёт этот PID браузеру. Журнал заморозок хранит **PID + время запуска** как идентичность, привязывает каждую запись к идентичности супервизора и scope конфига, и очищается при перезагрузке. Устаревшая запись пропускается, а не продолжается вслепую.

**GUI.** Трей-приложение с панелью должно выглядеть нативно, а не как вкладка браузера. На Linux webview сидит в GTK-окне, на Windows/macOS — в tao-окне: одна панель, один код, платформенный windowing. Панель двуязычна (RU/EN) с простым объяснением каждой настройки.

## Контуры

| Контур | Против чего |
|---|---|
| Кворум (≥2 сервиса согласны) | Один врущий IP-сервис |
| Пятистатусная IPv6-проверка | Утечка через путь, невидимый IPv4 |
| Транспортный зонд (1 с TCP) | Мёртвый туннель за ~1 с вместо ~10 с |
| Watchdog прокси-клиента | Процесс прокси умер, маршруты не сместились |
| Параноид-режим | Заморозка при изменении сети **до** перепроверки |
| Reputation guard | Выход с флагом proxy/datacenter |
| Гейт стабильности | Дребезг выхода доходит до приложения |
| Детектор утечки домашнего IP | Резидентный адрес за мёртвым туннелем |

Каждый контур — переключатель в панели с объяснением простым языком. Панель также показывает для каждого приложения: текущий статус, причину заморозки и время до принудительной остановки.

## Что бы я сказал себе два дня назад

1. **Туннель не падает громко.** Мёртвый туннель выглядит как «всё работает, просто с неправильного адреса». Нужна канарейка, семплирующая новые соединения, а не юзер, заметивший медленность.
2. **Один IP — это не один IP.** IPv4 и IPv6 — независимые выходы с независимыми режимами отказа.
3. **Замороженный процесс — обещание, а не syscall.** Проверь, что он остановился. Проверь, что PID всё ещё тот же процесс. Проверь, что супервизор, который заморозил, ещё жив.
